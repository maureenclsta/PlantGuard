PLANTGUARD AI PROJECT DOCUMENTATION Deep Learning Final Project

============================================================ 1. PROJECT
OVERVIEW ============================================================

Project Name: PlantGuard AI

Proposed Title: Real-World Plant Disease Classification Using Transfer
Learning and Explainable AI

Project Theme: Image Classification / Computer Vision

Project Type: Deep Learning application with a working prototype using
FastAPI.

Project Summary: PlantGuard AI is an application that helps users
identify plant species and detect visible plant diseases from leaf
images. Users upload a plant/leaf image, and a trained deep learning
model analyzes the image and returns the predicted class, confidence
score, and a Grad-CAM visualization showing image regions that
influenced the prediction.

The final prediction classes must follow the actual labels available in
the selected dataset. The project must not claim to recognize plant
species or diseases that are not represented in the dataset.

Main workflow: User uploads image -> Image preprocessing -> Trained deep
learning model -> Plant/disease class prediction -> Confidence score ->
Grad-CAM visualization -> Result displayed in the application

Important note: Grad-CAM explains which image regions influenced the
model prediction. It does not prove that the highlighted region is
medically or biologically the exact infected tissue.

============================================================ 2. PROBLEM
BACKGROUND AND OBJECTIVES
============================================================

Problem: Identifying plant diseases from visual symptoms can be
difficult for farmers and plant owners. Different diseases may have
similar visual symptoms, and image conditions such as lighting,
background, and weather can affect the appearance of leaves.

Proposed solution: Provide an image-based classification prototype that
predicts a plant/disease class from an uploaded image and communicates
the model’s confidence and visual explanation.

Objectives: 1. Build an image classification system using deep learning.
2. Use pretrained CNN models and transfer learning. 3. Prepare and
analyze a DOI-backed image dataset. 4. Compare model performance through
controlled experiments. 5. Evaluate model performance using suitable
classification metrics. 6. Explain predictions using Grad-CAM. 7. Deploy
inference through a FastAPI backend and a simple frontend. 8. Test model
robustness under selected image variations.

Target users: - Farmers and plantation workers. - Plant owners and
gardening communities. - Users who need preliminary visual information
about plant leaf conditions.

The application is an academic prototype, not a replacement for expert
agricultural diagnosis.

============================================================ 3. DATASET
============================================================

Selected dataset: Plant Species and Disease Detection using Deep
Learning on Plant Images Captured in Realistic Natural Field Conditions

Dataset repository: https://data.mendeley.com/datasets/bsr2vzhrzr/2

DOI: 10.17632/bsr2vzhrzr.2

Version: Version 2

Reported dataset information: - Total images: 9,469 - Plant species: 4 -
Plant species listed: Grapes, Groundnut, Guava, and Soybean - Original
dataset size: approximately 48 GB - Resized dataset size: approximately
5.04 GB - Reported image resolution: 2000 x 1126 - License: CC BY 4.0

Dataset source: Mendeley Data.

IMPORTANT DATASET VALIDATION TASK: Before finalizing the model design,
the team must download and inspect the actual dataset files and
documentation. Confirm: - The exact folder and file structure. - The
exact class names. - Whether each image has a disease label,
plant-species label, or both. - The number of images in every class. -
Whether healthy and diseased classes are present for each species. -
Whether metadata identifies capture sessions, plants, or image groups. -
Whether there are corrupted, duplicate, or unreadable images.

Do not assume the dataset contains a particular disease class until its
labels have been inspected. The final model output and project title
must match the labels actually provided.

Dataset preparation: 1. Inspect the dataset and documentation. 2. Create
a class distribution report. 3. Check corrupted and unreadable files. 4.
Check duplicates where feasible. 5. Confirm image-label consistency. 6.
Split data into training, validation, and test sets. 7. Avoid data
leakage. If images belong to the same plant, capture session, or source
group, keep related images in the same split when the metadata permits.
8. Resize images to the input size required by each pretrained model. 9.
Apply normalization compatible with the selected pretrained weights. 10.
Apply augmentation to training images only.

Potential augmentation: - Random horizontal/vertical flip when
appropriate. - Small rotations. - Random crop or scale. - Brightness and
contrast variation. - Mild color variation.

The augmentation strategy must preserve the meaningful plant symptoms
and must not create unrealistic training examples.

============================================================ 4. AI
MODELS AND TRANSFER LEARNING
============================================================

Planned models: 1. Custom CNN baseline trained from scratch. 2.
MobileNetV2 pretrained on ImageNet. 3. ResNet50 pretrained on ImageNet.
4. EfficientNet-B0 pretrained on ImageNet (optional, depending on time
and compute).

Transfer learning process: 1. Load pretrained ImageNet weights. 2.
Replace the original classification head with a new output layer
matching the dataset classes. 3. Initially freeze some or all
feature-extraction layers. 4. Train the new classification head. 5.
Fine-tune selected layers if appropriate. 6. Evaluate on validation and
test data. 7. Save the best model and its class mapping.

Model input: A preprocessed RGB image with the input dimensions required
by the selected architecture. A common starting point is 224 x 224,
subject to the model’s recommended preprocessing.

Model output: - Predicted class. - Confidence score. - Optional top-k
predictions, if useful.

The final output format depends on the verified dataset labels. If
labels combine plant species and disease (for example, a species_disease
class), the model may predict one combined class. If the dataset
provides separate labels, the team may consider separate prediction
heads, but only if the dataset structure supports this.

============================================================ 5.
EXPERIMENTAL DESIGN
============================================================

The project should demonstrate structured experimentation rather than
only training several models once.

Suggested experiments:

Experiment 1 - Baseline: - Train a simple CNN from scratch. - Record
training and validation performance. - Use this as a baseline for
comparison.

Experiment 2 - Transfer learning: - Train MobileNetV2 using pretrained
ImageNet weights. - Compare its performance with the baseline CNN.

Experiment 3 - Architecture comparison: - Train/evaluate ResNet50. -
Optionally train/evaluate EfficientNet-B0 if resources and schedule
allow. - Keep the data split and evaluation procedure consistent.

Experiment 4 - Augmentation comparison: - Compare training with
augmentation and without augmentation. - Keep other settings as
consistent as possible.

Experiment 5 - Robustness test: - Test selected image variations such as
lower brightness and mild blur. - Compare performance against the
original test images. - Clearly state that these are controlled
robustness tests, not a complete field validation.

For fair comparison: - Use the same train/validation/test split. - Use
the same class mapping. - Document image size and normalization. -
Record optimizer, learning rate, batch size, epochs, and fine-tuning
strategy. - Select the final model based on validation results, then
report final test performance only after model selection. - Do not tune
repeatedly on the test set.

Metrics: - Accuracy. - Precision. - Recall. - Macro F1-score. -
Confusion matrix. - Training time. - Inference time. - Model size.

Macro F1 is useful when class counts are imbalanced because it gives
equal weight to each class. Include per-class metrics where possible.

Analysis: - Identify classes that are frequently confused. - Explain
possible reasons for errors. - Discuss overfitting or underfitting using
training/validation curves. - Discuss the trade-off between model
performance, model size, and inference speed.

============================================================ 6. GRAD-CAM
/ EXPLAINABLE AI
============================================================

Purpose: Grad-CAM provides a visual explanation of image regions that
contributed to a selected model prediction.

Proposed display: - Original uploaded image. - Grad-CAM heatmap. -
Optional overlay of the heatmap on the original image. - Predicted class
and confidence.

Interpretation: The heatmap is an explanation of model
attention/activation for the prediction. It must not be described as a
precise disease segmentation mask or definitive localization of infected
tissue.

============================================================ 7.
APPLICATION FEATURES
============================================================

Core features: 1. Image upload. 2. Image preview. 3. Plant/disease class
prediction based on dataset labels. 4. Confidence score. 5.
Healthy/diseased status only if supported by the dataset labels. 6.
Grad-CAM visualization. 7. Low-confidence warning. 8. Clear error
message for invalid file types or unreadable images.

Low-confidence handling: Choose a confidence threshold using validation
data. If the top prediction is below the selected threshold, display a
message such as: “Unable to confidently identify this image. Please
upload a clearer image.”

Do not choose an arbitrary threshold without documenting the reason.

Suggested user interface: - Project name and short description. - Upload
area. - Analyze button. - Original image preview. - Predicted
plant/disease class. - Confidence score. - Status, if supported by
labels. - Grad-CAM result. - Short disclaimer that the result is an AI
prediction and not expert diagnosis.

============================================================ 8. SYSTEM
ARCHITECTURE AND FASTAPI
============================================================

Proposed architecture:

Frontend -> User uploads image -> Sends request to FastAPI

FastAPI backend -> Validates uploaded file -> Preprocesses image using
the same inference preprocessing as training -> Loads the selected best
model -> Runs prediction -> Generates Grad-CAM visualization -> Returns
prediction and visualization information

Frontend -> Displays prediction, confidence, and Grad-CAM

Suggested API: POST /predict - Accepts an image file. - Returns
predicted class, confidence, status if supported, and Grad-CAM output or
image URL/base64 representation.

Optional endpoints: GET /health - Returns API health status.

GET /classes - Returns the supported class names.

Example response structure (illustrative only; replace placeholder
values with actual model output): { “predicted_class”:
“CLASS_FROM_DATASET”, “confidence”: 0.952, “status”: “Diseased”,
“gradcam_available”: true }

The API must use the exact same class-index mapping and preprocessing
configuration as the trained model.

============================================================ 15. RISKS,
LIMITATIONS, AND MITIGATION
============================================================

Risk 1: Dataset labels do not support the intended disease classes.
Mitigation: Inspect the actual files and documentation before fixing the
final classification scope.

Risk 2: Dataset is very large. Mitigation: Use the resized version if it
is officially provided and suitable. Use efficient data loading, resize
to model input size, and avoid unnecessary duplicate copies.

Risk 3: Class imbalance. Mitigation: Inspect class counts. Consider
class weights or a suitable sampling strategy. Report macro F1 and
per-class metrics.

Risk 4: Data leakage. Mitigation: Use metadata/group information to keep
related images in one split where possible. Document the split strategy.

Risk 5: Model overfitting. Mitigation: Use validation monitoring,
augmentation, regularization, and appropriate fine-tuning.

Risk 6: Poor real-world generalization. Mitigation: Run brightness/blur
robustness tests and discuss the limits of the dataset. Do not claim the
model works for all plants or field conditions.

Risk 7: Grad-CAM misleading interpretation. Mitigation: Describe it as a
visual explanation of model activations, not precise disease
localization.

Risk 8: Integration problems. Mitigation: Freeze the inference interface
and class mapping early. Test the API with a dummy model before the
final model is ready.
